# Hex Tunnel 1.0.0-rc.19

Fecha: 2026-08-05

## Corrección principal

La instalación AMD64 podía cambiar accidentalmente `/tmp` de `root:root 1777` a modo `0700` al preparar una descarga verificada. APT dejaba entonces de crear archivos temporales para la validación de firmas y mostraba errores como:

```text
Couldn't create temporary file /tmp/apt.conf.* for passing config to apt-key
```

Si `unattended-upgrades` adquiría simultáneamente el lock de DPKG, Sing-box u otro componente podía fallar con:

```text
Could not get lock /var/lib/dpkg/lock-frontend
```

## Cambios

- Se añade `bin/hextunnel-package-manager` como ejecutor único de APT, DPKG y `apt-mark`.
- `/tmp` se valida y repara como `root:root 1777` antes de cada operación protegida.
- Las descargas verificadas ya no cambian permisos de directorios padre existentes.
- WARP, Sing-box y BadVPN utilizan el ejecutor protegido.
- APT aplica `DPkg::Lock::Timeout` y `APT::Update::Lock::Timeout`.
- DPKG vuelve a intentarse únicamente cuando el error corresponde a una carrera confirmada de lock.
- El instalador nunca elimina archivos lock ni termina `unattended-upgrades`.

## Recuperación de una VPS afectada

Cuando el instalador vuelva al prompt:

```bash
sudo chown root:root /tmp
sudo chmod 1777 /tmp
stat -c '%U:%G %a %n' /tmp
```

La salida debe ser:

```text
root:root 1777 /tmp
```

Después se debe esperar a que finalice el proceso que posee el lock. No se deben borrar archivos de `/var/lib/dpkg` ni terminar el proceso por la fuerza.

## Validación automatizada

La prueba de regresión reproduce:

1. un directorio temporal con modo `0700`;
2. un lock real simulado de `unattended-upgr`;
3. un primer fallo de DPKG por carrera;
4. reparación a `1777`;
5. espera segura;
6. reintento exitoso de DPKG.
